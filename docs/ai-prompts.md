# AI Prompt 与问题解决记录

> 这份记录按**问题 → 我给 AI 的 Prompt → AI 产出 → 我的判断与改动**写，尽量保留真实的失败与返工，而不是只写成功路径。

## 0. 我的使用原则

1. **AI 用来扩大搜索空间，不用来替我做判断。** 事实性的东西（各厂商协议细节）让 AI 去查并给出处；架构取舍、边界条件由我拍板。
2. **让 AI 写"契约"，不让 AI 写"整体"。** 并行开发时先定接口（`docs/CONTRACT.md`），再让不同执行者各自实现，否则拼不起来。
3. **AI 产出的每一行代码都要能被测试证伪。** 本项目 140 个测试里有相当一部分，就是为了证明"AI 写的这段确实按我说的做"。
4. **失败记录比成功记录有价值。** 下面第 5 节全是踩坑，这些才是面试里能聊的东西。

## 1. 题目解析：从 docx 到可执行清单

**问题**：题目是 `.docx`，且混排了两部分（vibe coding / 架构设计），容易漏要求。

**Prompt 要点**
> 用 python-docx 按文档顺序提取段落与表格（包括 style 名），输出成纯文本，保留编号列表结构。

**AI 产出**：一个 30 行的提取脚本。

**我的判断与改动**：第一次输出是乱码（Windows 控制台 cp936 + stdout 重定向），改成"写 UTF-8 文件再用读取工具看"，并把表格按 `R{i}: cell || cell` 展开——这一步让我发现"注意事项"和"提交内容"里的关键约束（比如"不要给 API"、"一个模块选一道题"）。

**结果**：得到一份带编号的要求清单，直接变成后来的评分自检表。

## 2. 架构题事实核查：让 AI 查证，纠正了两处硬伤

**问题**：架构题要讲"Claude Code vs OpenAI-compatible function calling"和"Agent memory 框架"，凭印象写很容易错，面试官一问就露馅。

**Prompt 要点**（两份并行任务）
> 做事实核查型调研，区分「确认到的事实（附官方文档/GitHub 链接）」与「你的工程判断」，不要编造 API 细节。重点：① DeepSeek/OpenAI-compatible 的 tool_calls 结构、流式分片与 reasoning_content 回填规则；② Anthropic tool_use/tool_result 的 block 结构（架构题对比用）；③ OpenHands 实际的状态枚举与 EventStream 模型。

**AI 产出**：两份带出处的事实清单。

**纠正的两处（重要）**

| 我原本以为 | 事实 | 影响 |
|---|---|---|
| 思考过程默认不回填 | DeepSeek 的推理模型**不接受**把 `reasoning_content` 放回请求；而有些厂商（如 GLM 交错思考）反而要求原样回传 | 本项目只对接 DeepSeek，所以固定 `ModelProfile.backfill_thinking=False`；"各家要求相反"这个结论写进架构题答案，不作为本项目的实现负担 |
| OpenHands 有 `AGENT_RUNNING` 状态 | 实际 12 个状态里**没有** `AGENT_RUNNING`；`EventStream` 是 append-only 多写者总线，不是严格单向流 | 架构题答案改写；代码里的 `state` 取值也只用 `idle/busy/waiting_tool/paused` |

**结果**：`config.py` 的 `ModelProfile` 注释直接引用这些结论；架构题第五篇的对比表也来自这里。项目最终按需求收窄为只支持 DeepSeek，多厂商调研成果保留在架构题答案里。

## 3. 一次方向纠偏：架构题不写代码

**问题**：我在方案里把架构题写成了"每篇都要落地到实现"，看起来像要交 5 个模块的代码。

**用户反馈**（原话）："架构设计题不用代码实现，你有没有仔细阅读文档"。

**我的处理**：回去逐条核对题面，确认：
- 第二部分原文是"5 个模块，一个模块选一道题目**回答**"；
- "提交内容（代码链接/README/AI Prompt）"紧跟第一部分的"要求3"，属于 vibe coding；
- 第 3 条"用大模型来帮助你思考，而不是用大模型来帮你完成任务"——**这句是筛选条件**。

**改动**：架构题交付物改成 `D:\AI\architecture-answers\` 下的 5 篇纯 Markdown，与代码仓库彻底分开；代码仓库里删掉 `docs/architecture/`；架构题里代码只作一句话论据。

**教训**：AI 很容易把"相邻要求"合并成"同一份交付物"。读题时要把"提交内容"绑定到它前面的那一段，而不是整份文档。

## 4. 并行开发：先写契约，再分头实现

**问题**：项目要同时做 5 个工具、会话持久化、context 组装压缩、主循环、140 个测试，串行写太久。

**Prompt 要点**
> 你要实现的是 `agent/tools/` 下的 5 个工具，**只允许改这 6 个文件**，接口以 `docs/CONTRACT.md` 第 1 节为准；不允许修改 `base.py` / `registry.py` / `config.py`。测试用 `unittest`，离线，不 import `agent.session`（那是另一个人的活）。

**AI 产出**：两个执行者分别交付工具层与会话/上下文层，各自带测试。

**我的判断与改动**：
- 契约里明确写了"工具函数第一个参数叫 `ctx` 时自动注入 `ToolContext`"，这条避免了双方对"todo 怎么拿到 session"的来回确认；
- 交付后我做了三件事：跑全量测试、抽查 `todo.py`（确认没有模块级全局状态）、用 `builtin_registry()` 验证 5 个工具 schema 的 `required` 是否正确。

**结果**：110 个测试一次性通过，没有出现接口对不上的返工。

## 5. 真实 bug 记录（这些才是重点）

### Bug 1：`f-string` 里嵌套转义引号 → SyntaxError

**现象**：`python -m agent` 直接 SyntaxError，但单元测试全绿（因为没覆盖 CLI）。

**原因**：Python 3.11 的 f-string 表达式里不允许出现反斜杠转义，`f"{Style.dim(f\"...\")}"` 在 3.12 才合法。

**修复**：把内层表达式提前算成变量 `meta`，再在外层 f-string 里引用。

**教训**：AI 很容易写出语法边界上的代码（尤其是长嵌套）。**测试没覆盖到的入口等于没写**——后来补了 `python -m agent --list-sessions` 的 CI 冒烟。

### Bug 2：脏 JSON 修复逻辑存在两个入口

**现象**：`test_single_quotes_and_trailing_comma` 失败——`{"action": 'list',}` 应该被修复，却返回 `{}`。

**原因**：修复逻辑只在 `parser._try_json` 里有，而 `ToolCall.from_openai` 走的是 `types._safe_json_object`，那里只做了去围栏。

**修复**：把三级修复（原样 → 去围栏 → 补引号/去尾逗号）补进 `_safe_json_object`。

**教训**：同一件事有两个入口，是 AI 生成代码的典型问题。写契约时应该把"唯一入口"写死。

### Bug 3：`busy` 测试为什么测不出 busy

**现象**：`test_busy_session_is_rejected` 失败，明明先 `acquire()` 了同一把锁，`run()` 却成功进入。

**原因**：`SessionStore` 内部方法会嵌套加锁，所以用的是 `RLock`（可重入）——同一个线程自然可以重入。

**修复**：测试改成"另一个线程持有锁"（这也更接近 CLI 的真实形态：请求跑在 worker 线程）。

**教训**：**用可重入锁的地方，"同线程占用"不能模拟并发**。这个坑不写下来下次还会踩。

### Bug 4：`FakeLLM` 脚本耗尽导致的"假失败"

**现象**：`max_steps` 测试报"内部错误：AssertionError: FakeLLM 脚本已耗尽"。

**原因**：`max_steps=2` 会调用 2 次 LLM，但脚本只给了 1 条工具响应。

**修复**：补齐脚本；同时确认这个异常被 `loop.py` 的最外层兜底捕获（说明兜底逻辑是对的）。

**教训**：测试替身也要遵守"调用次数契约"，否则失败信息会误导方向。

### Bug 5：异步结果注入用错 role

**问题**：异步任务完成后，结果怎么放回对话？

**AI 的第一版**：复用 `role="tool"` + 原来的 `tool_call_id`。

**我的判断**：不行。同一条 assistant 消息的 `tool_call_id` 已经被"已受理"结果占用了，重复用会违反协议（Anthropic 明确要求一一对应，OpenAI 系行为未定义）。

**改成**：`role="user"` + `[异步工具完成]` 前缀，并在文档里写明理由。这也是 `docs/system-design.md` 的 ADR-7。

## 6. 数字是怎么来的

**压缩效果**（30 轮 / 120 条消息，队友跑的压力脚本）：

| 场景 | before | after | 层 | LLM 调用 |
|---|---|---|---|---|
| budget=1500 | 33959（2263.9%） | 1338（89.2%） | L3 | 0 |
| 反推 0.70 水位 | 33959（70.0%） | 7105（14.6%） | L1+L2 | 1 |

**我的复核方式**：不相信"压下来了"这句话，要求给出 `before/after` 的 token 数、触发层、是否调用 LLM、工具配对是否完整（1/1、6/6）——这四个数缺一个就说明压缩可能把配对截断了，请求会 400。
